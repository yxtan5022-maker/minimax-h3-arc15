# 路径 B：激进量化（INT4 / GGUF）

## 背景

H3 扩散主干 33.1B 参数（含 13B AdaLN 分支），文本编码器 Qwen3-VL-32B。
官方 INT8 + NVFP4 最小组合约 42.5GB，远超 24GB 内存，必须继续压缩。

## 体积预算表（估算）

| 量化档 | DiT | 文本编码器 | VAE | 合计 | 能否进 24GB |
|---|---|---|---|---|---|
| INT8 (pruned) 官方 | ~21GB | ~15.7GB | ~5.8GB | ~42.5GB | ❌ |
| INT4（torchao/自行） | ~11GB | ~8GB | ~3GB | ~22GB | ~勉强（建议+页文件） |
| Q2~Q4（GGUF 社区） | 8~13GB | — | — | 变量 | ⚠️ 视版本 |

社区动态（2026-08）：
- 已有人放出 GGUF 格式 Q2-Q4 量化版（"INT4 抢跑，3060 12G 可玩"）。
- 但**官方无 GGUF**，网络上存在假文件风险 → 只从可信源下载并校验 SHA。
- 视频扩散模型的量化 ≠ LLM 量化：质量退化、采样发散是已知风险。

## 关键问题

1. 量化质量：INT4 DiT 出片是否还能看？AdaLN 分支是否特别敏感？
2. 编码器量化到 INT4 后指令遵循是否崩？
3. 加载路径：GGUF 走 llama.cpp（CPU）；diffusers 走 torchao INT4（PR #14355 未合并）；
   ComfyUI 目前只有 INT8/NVFP4 官方文件。
4. 24GB 内存 + ~22GB 权重：操作系统 + 运行时 + 激活值余量极小 → 大概率仍需页文件 + 流式兜底。

## 验证步骤（M2）

- [ ] 收集可信社区量化版本清单（HF tag 搜索：minimax-h3 / gguf / int4），校验来源
- [ ] 若无可信版，用 torchao 将 `pruned_int8_convrot` 自行量化到 INT4
- [ ] 加载测试：能否在 24GB 内完成 load 而不 OOM（先不推理）
- [ ] 质量对比：INT8 vs INT4 同 prompt 出片对比
- [ ] 记录最小可行组合的体积/加载时间/首 token 时间

## 预期

- INT4 是唯一可能"全内存常驻"的方案，但大概率仍需与路径 C（页文件/流式）组合。
- 这是本项目最可能"出片"的关键路径，值得投入最多精力。
